# Navigation Rail Capabilities — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Move the runtime/model pickers + Start/Stop off the top bar into a mural **capability** reached from the `EditorShell` navigation rail, leaving chat as the main content.

**Architecture:** Adopt mural's native capability/module shell (the `platform.mu` pattern). A `shell module` declares a **Runtime** `Capability` whose backing `RuntimeManagementService` (a `ServiceBase`) owns the picker + coordinates chat binding and renders into the shell's side pane; `EditorShell x:root {}` auto-populates the rail. Chat (with the instrument panel) remains `ContentHostService.Content`.

**Tech Stack:** Electron + mural `0.67.1` (TS renderer, `.mu` markup compiled by the mural CLI via `npm run compile:mu`), vitest.

**Spec:** `docs/specs/2026-11-20-navigation-rail-capabilities-design.md`

## Global Constraints

- House style: Allman braces, **no semicolons**, PascalCase public methods/interfaces, hoisted `private static readonly` string literals, view-models/services bind by name. `.mu` labels stay inline.
- mural `0.67.1`. `.mu` is compiled by the mural CLI (`scripts/compile-mu.mjs`); it supports `shell module`, `Capability`, and `include "icons/x.svg" as Key` (SVG→geometry).
- `.mu.js` are gitignored and regenerated by `npm run compile:mu` (runs in `dev`/`build`/`pretest`).
- Reference implementation to mirror: mural repo `demo/platform/platform.mu`, `demo/platform/groups/controls.module.mu`, `demo/platform/groups/controls-service.mts`, `demo/platform/demo-platform-icons.mu`.
- Don't change supervisor/backend/protocol, the `HarnessPickerViewModel`, `ChatViewModel`, `InstrumentPanelViewModel`, or `HarnessPanel.mu`/`Chat.mu`/`InstrumentPanel.mu` templates — they are reused verbatim.
- Builds/tests: vitest + typecheck + `npm run build` run locally; end-to-end run needs the hive supervisor at `ws://192.168.1.101:8778` (`HARNESS_SUPERVISOR_URL`).

## Review Focus

- **No supervisor URL (direct-backend fallback).** `main.ts` currently falls back to a direct `ChatViewModel` when `HARNESS_SUPERVISOR_URL` is unset. The new shell must still render: fallback keeps chat as the content host, with no harness attached (picker absent/disconnected), and must not throw. → Task 5 test.
- **Capability resolved before Attach.** `EditorShell` may auto-resolve/select the capability (running `RuntimeManagementService`'s ctor) before `main.ts` injects the client; `Picker` is then `null` until `Attach`. The pane binding (`$Picker`) must tolerate null→set (INPC). → Task 2 test + Task 6 run.
- **Single shared supervisor connection.** The singleton service and the rail pane must use the *same* picker/connection — no second `SupervisorClient`. → Task 2.
- **Start/stop still drives chat.** A ready harness binds the chat client; stop/clear unbinds — unchanged behavior, now across pane↔content-host. → Task 2 tests + Task 6 run.
- **Rail renders with one capability.** The rail/side pane must show and auto-select the single Runtime capability at launch (not require a user click). If `EditorShell` doesn't auto-select, select explicitly. → Task 6 run.
