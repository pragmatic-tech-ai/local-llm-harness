# Supervisor URL Setting — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the supervisor URL a persisted, in-app setting edited through a Plexus-style mural settings service, driving the supervisor connection with live reconnect; the `HARNESS_SUPERVISOR_URL` env var becomes a first-run default.

**Architecture:** Adopt mural's `ApplicationSettings` host-seam (framework owns the service + rail launcher; the app supplies a persistent `ISettingsStore`, the `SettingDefinition`s, a settings contribution, and a minimal settings page). Persistence is `userData/settings.json` via a preload→main IPC bridge (sync snapshot on load, async save). The Runtime capability reads/subscribes the `supervisor.url` setting and owns the `SupervisorClient` lifecycle, reconnecting live on change.

**Tech Stack:** Electron (main/preload/renderer) + mural `0.67.1` (TS renderer, `.mu` markup via `npm run compile:mu`), vitest.

**Spec:** `docs/specs/2026-11-20-supervisor-url-setting-design.md`

## Global Constraints

- House style: Allman braces, **no semicolons**, PascalCase public methods/interfaces, hoisted `private static readonly` string literals, view-models/services bind by name; VMs extend `Observable`. `.mu` labels stay inline.
- mural `0.67.1`. Settings symbols imported from `@pragmatic-tech-ai/mural/framework`: `ApplicationSettings`, `SettingsStoreKey`, `type ISettingsStore`, `SettingDefinition`, `SettingKind`, `Setting`, `SettingsLauncherService`, `SettingsContributionKey`, `type ISettingsContribution`; `DialogService` from the same barrel.
- Renderer never touches the filesystem — all persistence flows through the preload bridge to the main process.
- `.mu.js` are generated by `npm run compile:mu` (runs in `dev`/`build`/`pretest`).
- Reference shape (do not import from it — it's a different app): Plexus `ElectronSettingsStore`, `settings.ts` (main), `settings-page.ts`, `settings.resources.mu`, `*.module.mu` `.settings:` blocks.
- Don't change the supervisor/backend protocol, `HarnessPickerViewModel`'s picker↔supervisor logic, `ChatViewModel`, or `HarnessPanel.mu`/`Chat.mu` templates.

## Review Focus

- **First run, env unset.** No saved value and no `HARNESS_SUPERVISOR_URL` → `supervisor.url` is empty, the picker is inert, nothing throws, and a direct `HARNESS_BACKEND_URL` (if set) still binds chat. → Task 5 test + Task 6 run.
- **Missing/corrupt settings file.** `settings.json` absent or unparseable → store `Load()` returns `{}`, definition defaults apply, no throw. → Task 1 test.
- **Clearing / changing the URL mid-session.** Editing `supervisor.url` (including to empty) while a harness is live must disconnect the old `SupervisorClient` cleanly, unbind the chat, and — if non-empty — connect the new one and re-attach the picker, with no leaked connection or double subscription. → Task 5 tests.
- **Rapid successive edits.** Two quick changes must not leave an orphaned connected client; each `ApplyConnection` disconnects the prior client before connecting. → Task 5 test.
- **Settings gear present at launch with one contribution.** The rail footer shows the gear and it opens the dialog with the `supervisor.url` row; editing writes through to the store. → Task 6 run.
